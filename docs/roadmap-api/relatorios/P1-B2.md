# P1-B2 — Aceitar `Authorization: Bearer` na /v1

**Status:** pronto
**Commit(s):** `988961d` — feat(P1-B2): /v1 aceita Authorization Bearer
**SQL rodado pelo Agadir:** não se aplica

## O que foi feito
- `api/v1/[...path].js`: só a leitura da chave mudou. `resolveApiKey` está igual.
  - Ordem: `x-api-key` → `Authorization: Bearer <chave>` → `?key=`. Vale a primeira preenchida.
  - Função `bearerKey(header)`, que aplica a regex `^bearer\s+(.+)$` sem diferenciar caixa:
    - aceita um ou mais espaços depois do prefixo e faz trim da chave;
    - header sem o prefixo `Bearer`, `Bearer` vazio ou ausente devolve `null`, e a leitura segue
      para a próxima opção.
  - Comentário no código: na /v1 o Bearer é a **chave da integração**
    (`company_integrations.api_key`), não o JWT do Supabase.
  - Nenhum erro novo: sem chave válida, continua `401 { error: 'invalid_api_key' }`.

## Riscos ou pendências
- `x-api-key` errada + `Bearer` certa dá 401. É o comportamento pedido (a primeira chave
  preenchida vale, mesmo errada). Vale citar na doc da P1-Z: mande só um dos dois headers.
- O allowlist e os docs não têm o valor da chave (só `FLOWMATE_TEST_KEY` pelo nome).
