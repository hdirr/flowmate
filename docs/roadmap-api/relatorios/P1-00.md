## Riscos ou pendências
1. **`custom_fields.type` × `field_type` quebra a API e também o front.** O `grep -rn custom_fields src`, pedido pelo tutor, mostrou:
   - **Na API**, `api/_lib/v1handlers.js` seleciona `type` nas linhas 42, 101 e 121. Efeitos esperados pelo código (a confirmar com curl na P1-00b):
     - `GET /v1/fields` devolve `[]`;
     - `GET /v1/contacts` devolve `fields: {}`;
     - `PATCH /v1/contacts` e `POST /v1/leads` devolvem todo campo em `unknown_fields` e não gravam.
   - **No front, a tela não usa `field_type`.**
     - `ContactPanel.jsx:75`, `LeadPanel.jsx:78` e `Automations.jsx:87` criam com `{ name, type, options }`. O insert manda a coluna `type`, que não existe, então **criar campo falha** sem aviso (`store.js` ignora o erro).
     - `ContactPanel.jsx:210-227`, `LeadPanel.jsx:235-252` e `Automations.jsx:277/289/296` decidem o input por `field.type`. Como a linha do banco vem com `field_type`, `field.type` é `undefined` e **nenhum input aparece**: só o nome do campo e a lixeira.
   - Ou seja: pelo código, campo personalizado não funciona em lugar nenhum hoje. Isso afeta o teste (b) da P1-00b ("o valor aparece na tela do contato"). Ver Pergunta 1.
2. **`supabase_whatsapp_cache.sql` foi rodada**: `whatsapp_instances.updated_at` existe e tem gatilho. O HANDOFF diz que não. Fica para corrigir na P1-Z.
3. **Não existem colunas `asaas_*`** em `companies`, ao contrário do que diz o HANDOFF. O código em `api/` não usa nenhuma. Fica para corrigir na P1-Z.
4. **`company_id` nulo:** 0 em `crm_contacts`, 0 em `crm_leads` e **5 em `crm_stages`**. Essas etapas não aparecem na API nem na tela. Só registrado, sem correção.
5. A FK `custom_fields.company_id → companies` existe, mas a migração do repo também cria `custom_fields`. O banco segue a migração do repo, só que o código não segue o banco.
