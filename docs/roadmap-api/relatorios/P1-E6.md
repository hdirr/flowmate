# P1-E6 — `PATCH /v1/conversations/{id}`

**Status:** pronto · **Commit:** `d6e519e` — feat(P1-E6): PATCH /v1/conversations/{id} · **SQL:** não se aplica
**Processo:** simplificado (bloco do tester).

## O que mudou
- **`api/_lib/v1/conversations.js`, `updateConversation`:**
  - `{ "state": "automation" | "human" }`;
  - reaproveita o `setConversationState` de `api/_lib/conversations.js`, o mesmo do botão da
    tela, com `actorUserId` nulo;
  - **resposta:** a Conversa no formato do GET, sem `last_message`;
  - **mesmo estado** → 200 sem update;
  - **erros:**
    - grupo → 422 `unsupported_for_group`;
    - `state` inválido ou ausente → 400 `invalid_state`;
    - corpo que não é objeto → 400 `invalid_body`;
    - inexistente, de outra empresa ou id que não é UUID → 404 `conversation_not_found`.
- **Sem evento:** `conversation.state_changed` continua `available: false` (só sai na P1-W1),
  então a rota não dispara nada.
- **`router.js`:** rota `PATCH conversations/:id`.
- **Contrato:** comportamento, erros, `state_by` nulo pela API e efeito no `message.received` e
  no `POST /v1/messages`.

## Como testei
- **Local:** roteamento (`PATCH conversations/:id`; `DELETE` → 405 com `GET, PATCH`) e as 4
  validações sem banco.
- **Produção** (`d6e519e`), **só na conversa do contato de teste "Teste S4b"** (telefone
  fictício). Ela terminou em `automation`, como começou; só o `state_since`/`updated_at` ficaram
  com a hora do teste.

| Caso | Resultado |
| --- | --- |
| `automation → human` | 200, `state: human`, `state_by: null` |
| `human` de novo | 200, `state_since` inalterado (no-op) |
| `human → automation` | 200 |
| Grupo | 422 `unsupported_for_group`; o estado do grupo não mudou |
| `state: "pausado"` / `{}` | 400 `invalid_state` |
| Inexistente / não-UUID | 404 `conversation_not_found` |
| Bearer / sem chave | 200 / 401 |
| Smoke | idêntico ao anterior |

## Perguntas / pendências
1. **`state_by` nulo pela API**, igual a quando o dono responde pelo celular. Hoje não dá para
   saber, pelo banco, se a pausa veio da API ou do celular. A P1-W1 resolve isso no evento
   (`changed_by: "api"`), mas não na coluna.
2. **O 409 do `POST /v1/messages` com a conversa em `human` não foi refeito aqui.** A tentativa
   usou o campo errado e voltou 400 `missing_content`, sem enviar nada. Não repeti para não
   arriscar um envio real de WhatsApp. O 409 é comportamento antigo, já validado antes do
   roteiro, e o `PATCH` usa o mesmo estado que ele lê.
