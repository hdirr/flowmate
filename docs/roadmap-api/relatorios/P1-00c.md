## Conferências antes de codar
- **Acesso ao banco:** as três telas (`ContactPanel.jsx`, `LeadPanel.jsx`, `Automations.jsx`)
  passam por `db.customFields`. Nenhum componente lê `custom_fields` direto do Supabase
  (`grep -rn "custom_fields" src` só acha `store.js`).
- **Tipos oferecidos:** `text`, `number`, `date` e `select` nas três telas, iguais ao CHECK do
  banco. O CHECK não foi alterado.
- **Onde fica o valor:** `crm_contacts.fields`, chaveado pelo **id** do campo. É o mesmo formato
  da API, confirmado no teste (c) abaixo.

## O que foi feito
- `src/lib/store.js`:
  - helpers `fieldFromDb` (`field_type → type`) e `fieldToDb` (`type → field_type`; tipo fora do
    CHECK lança "Tipo de campo não suportado");
  - `customFields.list/create/update` passam pela conversão;
  - `create` e `update` lançam erro quando o banco falha (antes o erro era ignorado);
  - `list` e `remove` logam o erro.
- `ContactPanel.jsx`, `LeadPanel.jsx`, `Automations.jsx`: só a função `createField` mudou.
  - Ela captura o erro e mostra com `alert()`, sem fechar o formulário.
  - O botão também sai de "criando" (antes ficava travado para sempre).

## Desvios do plano
- **Aviso com `alert()`**, porque é o padrão que o app já usa para erro (`Automations.jsx`, `Chats.jsx`, `Users.jsx`). Não existe toast no projeto.
- **Componentes alterados**, além do `store.js`: o item 3 do tutor (o erro precisa aparecer na tela) exigia o `try/catch` em quem chama. A conversão de tipo ficou só no store.
